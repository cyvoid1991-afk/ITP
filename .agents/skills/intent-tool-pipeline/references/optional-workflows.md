# Optional documentation work

Assess operator documentation **after implementation and before candidate packaging**. Compare the current README, product SKILL, examples, code, and tests for the changed usage path. If the docs are accurate and findable, leave them unchanged. A missing command, false behavior claim, or misleading result interpretation is an ordinary completion defect to fix before release; it is not optional merely because the separate rework skill is optional.

Suggest `$rework-product-docs` when a broader navigation or usage redesign would materially help. If the user has already delegated that documentation work, execute it within the authorized scope instead of asking again. Keep its self-contained procedure, evidence review, and file ownership; do not use it to alter product behavior or to claim independent verification. The pipeline's existing tests, candidate inspection, and verifier still decide release readiness.

After a release, a local documentation-only correction can be recorded as a new source delta with its actual checks. An authorized local patch/full package may use `$minor-tool-revision` when its qualification and [local-delivery requirements](../../minor-tool-revision/references/local-delivery.md) hold, including package-only delivery with current source evidence. Independently assembled local outputs belong in repository-root `deliverables/`. Do not rewrite the prior archive or its evidence. If the user requests a **new formal verified release** of documentation changes, route it explicitly through Workflow B as a documentation release request and apply its contract, verification, and packaging requirements; do not relabel an ordinary local correction or package as the old verified candidate. Keep historical records append-only.
