# Hypothetical decision examples

Read these when interpreting a normal rework, a material conflict or insufficient
evidence. The products, commands and numbers below are illustrative, not defaults
or executable instructions for the target product.

## Normal rework: reuse a stored result

A product documents `analyze` and `render`, but its operator SKILL sends every
request through `analyze`. Public CLI help and renderer tests establish that
`render` accepts a stored result without raw inputs or recomputation. The user's
request is to explain or redraw an existing result.

Create a goal route that distinguishes explanation from rendering and fresh
analysis. Put the stored-result format, renderer options and output checks in the
relevant operation reference; keep the SKILL's selection rule visible. Supply a
complete hypothetical render example using a controlled output path. Rewrite the
old unconditional analysis advice and update README links. Review the selected
path without relying on undocumented source knowledge; use existing safe renderer
checks if available. Leave accurate installation instructions unchanged.

## Material conflict: output units

A current README commits to milliseconds, but the implementation and tests emit
seconds. The same output value would produce materially different interpretation.

Document the observed behavior and commitment separately with evidence and version.
Flag the affected interpretation/conversion path and request a decision about the
supported contract. Do not silently rewrite the contract to seconds, insert a
conversion, or change code. Continue supported setup or inspection documentation
and make the unresolved boundary visible on the affected reading route.

## Insufficient evidence: partial distribution

A distribution supplies a README, CLI help and a sample summary; source and the
optional exporter are absent. The README mentions export without accepted options.

Rework known inspection and summary-interpretation paths, create an authorized
missing SKILL and explicitly identify the inspected snapshot. Keep export as an
unverified boundary; do not invent options, defaults or successful execution.
Ask for exporter evidence only if needed for that requested path. Report which
parts were document-reviewed and which checks could not run.

## Accurate content with poor reading boundaries

A product's README accurately documents substantial import, composition,
calculation and saved-result rendering workflows. Its SKILL links to README
headings, but a rendering request still requires finding its input contract,
integrity checks and output restrictions among unrelated calculation details.

Keep setup and first use in README, route goals from SKILL, and move the related
rendering contract and complete example together into a task reference. Group
other substantial workflows by their actual reading dependencies, preserving
public links where needed. Do not merely add another index to the same layout.
Walk a render-only request from the entry document; record any condition that
still requires source knowledge. Accurate content did not establish adequate
reading structure, and more files alone do not establish improvement.

## Adequate existing guidance

Requested inspection shows that representative goals already route to complete,
consistent instructions. A small inspection-only tool may fit in one concise
README and SKILL without further references. Preserve those files when splitting
would only add navigation. Report the structure rationale, paths and evidence
reviewed, including execution limits; do not manufacture edits to claim completion.
